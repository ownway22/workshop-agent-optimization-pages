    Act 2：找出表現不佳的地方¶

    Understand where it struggles · 不只看一個回答，而是找出反覆出現的問題。

    業務問題：哪些失誤會讓人重查、重做或交接不清？ 就像設備維護摘要若漏掉資料依據，下一位接手者仍得重新確認。本幕不是挑一個出錯回答來批評模型，而是找出有證據、值得優先改善的問題。

    目標¶

    向同一個 v1 重複提出 Exploring 題目，收集執行追蹤記錄（trace），讓 Insights 歸納哪些問題經常發生。先知道問題在哪裡，才知道下一步值得改什麼。

    項目 本幕安排
    現場主線 學員操作 · 必做：讀取 v1 追蹤記錄與 Insights 分析發現（findings），區分觀察與假設。
    閱讀與觀察位置 教材瀏覽器與獲授權的 Microsoft Foundry；只閱讀講師交付的本次證據。
    原指令執行位置 主要 Ubuntu VM 的第二場專用 Terminal、第二場專案根目錄，明確指定本組環境。
    時間 待講師試跑確認。

    前置條件¶

    進入本幕之前

    Act 1 的本組基準與本人登入已交付，且講師已放行本輪操作。先核對目前交付狀態，不要因為教材或操作網站可開啟就提交工作。

    本場課前完整探索為 36 題 × 3 次；課堂只循序操作 BLOCK、EVIDENCE、HERO、ACCESS 各一次。操作網站的四個情境不等於題集檔案的前四列，也不是完整 108 筆探索的替代品。

    已取得本次 Exploring 執行摘要、v1 追蹤記錄與分析發現的閱讀權限。記錄尚未送達或工作尚未完成時，先記錄狀態，不假裝已完成分析。

    需授權／可能計費

    下列操作會呼叫模型或啟動分析。取得授權後，從本場專案根目錄執行。不要為了等待結果，在同一個環境重複提交多個作業。

    操作步驟¶

    學員操作 · 必做¶

    1．循序操作四個情境¶

    位置：主要 VM 內的本組 Travel 操作網站。 講師放行後，由當輪操作者依序選取 BLOCK-01、EVIDENCE-01、HERO-01、ACCESS-01，每次確認輸入與收據，再按一次 Review travel request，等結果返回後才進行下一題。選情境不等於已送出，不連續點送出。

    證據檢視者展開 How your request was checked，對照政策工具的參數（arguments）、回傳結果（result）與回答；紀錄者從 Service details 記下情境、UTC 時間、Response ID、延遲、輸入／輸出 Token 用量與本組來源。畫面的 Active version 是路由資訊，不能單獨證明回應實際執行版本；仍需保留原始回應與執行階段紀錄核對。

    如果出現錯誤、重複請求或版本不符，停在該題記錄，不以成功的另一題代替。

    2．在 Foundry 找到同一次執行¶

    位置：本組 Microsoft Foundry → Agents → contoso-travel → Traces。 證據檢視者用操作時間、Response ID／追蹤資訊與實際版本找到 HERO 的同一次執行，展開工具呼叫與回傳。不要只選第一筆或只篩選名字相同的 Agent。

    紀錄者留下追蹤記錄識別資訊及一項可追溯的觀察，例如「預訂工具拒絕，但回答聲稱完成」。追蹤記錄尚未送達時先等候並核對範圍，不為了產生畫面再送一次付費請求。

    3．從單筆證據整理反覆問題¶

    位置：本組 Agent 的 Insights 或講師交付的分析發現。 對照每項發現的時間、版本及涵蓋的追蹤記錄；將一項發現分類為行為指示、工具／資料或證據不足，說明理由。單筆追蹤記錄只能支持該次觀察，是否反覆發生要看批次證據。

    若本組尚未有有效 Insights，就記下目前阻礙與可用的追蹤記錄，不把原版示範發現當成本組發現。下一個區塊說明課前完整資料；新增分析仍須符合 Step 4 的放行條件。

    課前與課堂界線：完整探索由講師預跑

    課程前：收集代表性的追蹤記錄¶

    Step 3．向 v1 提出 Exploring 題目¶

    課前完整預跑為 36 道 Exploring 題目，每題 3 次，共 108 個回答。每次使用新的對話，並保留回應的實際 Agent 版本與來源。這項工作不由全體學員各跑一次。

    重複提問的目的，是分辨偶然與規律。一次沒出錯不代表穩定，一次出錯也不代表所有情境都不好。

    付費工作依講師排程，探索先採循序執行。不要自行提高並行數或縮小已約定的題集，再把不同方式的延遲當成公平比較。

    驗證 Step 3 的產出¶

    • 檢查 script 的簡單／中等／困難摘要與失敗項目。
    • 在講師交付的本組唯讀結果中，找到回答、實際版本與摘要；原始紀錄位於主要工作副本的 .azure/<env>/questions/。
    • 在 Foundry 核對回應的實際版本及追蹤時間，不能只看請求標籤；遙測資料可能需要等候才送達。
    • 不把一份只有部分回答的產出誤當成完整 108 筆。
    詢問 Copilot：從題目摘要找線索

    將 <env> 換成你的環境名稱。

    請摘要 .azure/<env>/questions/exploring-v1-*.md。
從簡單到困難，延遲、Token 用量與工具呼叫如何變化？
哪些結果值得進一步讀追蹤記錄？請指出實際證據，不要猜測未執行的分數。

    Step 4．讓 Insights 閱讀追蹤記錄¶

    只在本組已放行時啟動一次

    本組未放行、已有工作執行中、先前工作失敗但尚未核准重試，或缺少必要追蹤記錄時，改讀講師交付的可驗證結果；沒有結果就記錄阻礙，不提交新工作。容量限制交由講師處理，不自行加額或縮小資料範圍來製造成功結果。

    本場 Insights 指向本組的 gpt-5 模型部署，由交付設定選定，不另建 insights-judge 別名。講師確認 Client、來源、權限、實際版本及時間窗後，才由當輪操作者執行：

    bash infra/05-insights.sh --label v1 \
  --environment "${AZURE_ENV_NAME:?請先完成本組環境交付}"

    預設時間窗為最近 3 小時，須確認包含本輪追蹤記錄。跨日時不直接沿用預設，也不自行拉大時間窗；交由講師核對費用、容量與要分析的版本。分析失敗時，不以空白結果冒充成功。

    時間窗不是版本隔離。 本地標籤、--label 與輸出檔名，不能單獨證明服務端只分析指定版本。還要核對實際分析範圍、時間窗內的版本來源與本組資料；同組工作沒有重疊，也不代表最近三小時完全沒有其他版本。範圍不清楚時先補證據，不用換檔名假裝完成隔離。

    驗證 Step 4 的產出¶

    1. 確認工作完成，而不只是已成功提交。
    2. 讀取 .azure/<env>/insights/findings.json。
    3. 在 Foundry 開啟 contoso-travel → Insights，核對分析發現與涵蓋的追蹤記錄。

    沒有分析發現、分析作業失敗與追蹤記錄尚未送達，是不同的狀況。不要把成功的空結果當成「所有問題都消失了」。

    課程中：讀一筆，再看一群¶

    1. 在 contoso-travel → Traces 選一筆 HERO 追蹤記錄。
    2. 依序看工具呼叫、政策檢查、預訂嘗試與工具回傳結果。
    3. 回到 Insights，對照相同問題涵蓋多少筆追蹤記錄。
    4. 將發現分成兩類：行為指示的問題與工具／資料的問題。需要更多證據時，保留不確定性。

    HERO 帶讀：行程寫出來，下一個人就能接手嗎？¶

    旅客想要的是能繼續處理的合規行程，而不只是一段完整文字。請直接使用本輪有效的 HERO 回應；若未取得，就使用有來源的本組預跑紀錄，沒有證據時不補造台詞或結果。

    故事進度 停下來看什麼 對接手者有什麼意義
    找到航班、飯店與租車 選項是否真的來自工具，條件是否符合需求？ 不必從頭確認是否有捏造的選項。
    檢查政策、組裝行程 是否取得明確政策結果，並對應選定的項目？ 知道判斷依據，而不是把「沒有被阻擋」當成完整合規證明。
    提交模擬預訂 預訂工具是否收到政策檢查結果 compliance_summary？實際接受或拒絕的原因是什麼？ 「行程已寫好」和「下一步工具接受」是兩件事。
    向旅客說明結果 回答是否清楚區分已完成、未完成與仍需補足的部分？ 接手者知道可以繼續什麼、還要查什麼。

    若工具拒絕，追查缺少的證據或不符的條件；若回傳 dry_run_success，核對成功的是模擬流程，不是真實訂位。不預設 HERO 一定失敗，也不因結果成功就跳過證據核對。

    回到半導體場景，維護資訊摘要可以協助交接，但不能只因文句完整，就當成已確認原因或可執行工單。這裡練的是查核與說清楚限制；實際維修判斷、核准與設備操作仍依既有授權流程進行。

    下一步先查哪個變因？¶

    不是所有問題都該換模型或加長提示詞。先提出有證據的假設，再選一個可驗證的變因；這張表不是自動根因診斷，也不授權本場額外修改工具、資料或權限。

    觀察到的線索 下一步先找的證據／變因 業務判讀
    工具可用，卻反覆漏查政策或把未完成說成完成 行為指示是否清楚要求先查證、揭露限制？工具呼叫順序是否符合要求？ 先改善工作方式，不把流暢敘述當成已交付。
    指示、資料與工具已核對，困難題仍不穩定 用同一評估條件驗證模型選擇，不能只看一個回答。 模型能力是可測的方向，不是憑名稱選更貴模型。
    搜尋結果為空但固定資料有項目，或總額無法核對 工具條件、資料範圍、單位、幣別及估價契約。 工具與資料簡化不能全算成模型失誤；先交負責人確認。
    後續評分理由與工具證據矛盾 評分表是否適用、評分模型是否誤判？先用既有紀錄人工核對。 評估本身也要查核，不改門檻來製造進步。
    權限、速率限制、來源缺漏或實際版本不符 環境、服務交付與資料完整性。 先記錄尚未完成或不可比較，不列成模型品質較差。

    對照半導體場景，這張表幫助團隊討論「下一筆改善時間該花在哪裡」。本場只練習判讀及核准範圍內的單一步驟，不把設備維護類比變成實際製程或設備變更。

    情境插畫：核對證據，不是操作截圖

    插畫不代表本次執行；判斷仍以本組實際工具回傳結果與追蹤記錄為準。

    選做：詢問 Copilot，整理 Insights 發現 
    請閱讀 .azure/<env>/insights/findings.json。
依涵蓋的追蹤記錄數量排序，每項用一句話解釋。
哪些像行為指示的問題，哪些需要檢查工具或資料？
請把可驗證的發現與假設分開，不要直接修改程式碼或雲端設定。

    完成條件¶

    以下為自行核對清單，本站不儲存完成進度。

    • 能指出本次分析的 v1、時間範圍、題數與重複次數。
    • 能用一筆追蹤記錄解釋回答與工具回傳結果的關係。
    • 至少一項判斷能追溯到 Insights 與實際追蹤記錄；沒有分析發現時如實記錄。
    • 沒有把失敗、資料尚未送達或部分回答說成完整成功。

    疑難排解¶

    狀況 下一步
    找不到最近的追蹤記錄 確認環境、標籤、送達狀態與分析時間範圍。
    Insights 失敗或觸及速率限制 先查實際工作與配額，由獲授權者處理，不重複提交多個作業。
    作業成功但沒有分析發現 與作業失敗分開記錄；不能直接推論沒有問題。

    詳細處理方式見疑難排解。

    這一步在 hill climbing 的位置¶

    我們看清楚哪些方向值得嘗試。但往前走之前，還需要同一個「高度計」：能對每個版本一致評分的評分表。
