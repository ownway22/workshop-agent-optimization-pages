    Act 2：找出表現不佳的地方¶

    目標¶

    我們站上山坡了——一次回答不能證明穩定性，需要多筆記錄才能觀察反覆出現的問題。我們將查看 v1 的執行追蹤記錄（Trace），並透過 Insights 理解歷史紀錄中反覆出現的問題。先知道問題在哪裡，才知道下一步值得改什麼。

    完成條件¶

    • 能指出 Act 1 執行的四個情境的 Trace ID。
    • 能理解 Insights 頁面中的具體改善建議。

    步驟¶

    1．使用 Foundry Traces 檢視歷史紀錄¶

    進入您的 Foundry project（proj-opt-g0*），依序點選 Microsoft Foundry → Agents → contoso-travel → Traces。檢視 Trace ID、狀態、Tokens、Estimated cost 等資訊。

    圖 1：Traces 介面參考。


    2．使用 Insights 歸納出具體行動¶

    點選 Insights 頁面，選取左側的一項分析發現，再於右側查看說明、關聯 Trace 與 Proposed fix，理解可採取的改善行動。

    圖 2：Insights 介面參考。


    以下依五張 Insights 畫面，整理 contoso-travel 的問題情境、肇因與具體改善建議。這些是待驗證的修正方向，需回到關聯 Trace、工具契約與指令確認；其中第三、第五項尚未確認安全修法，不應直接放寬合規規則。

    情境 肇因 具體建議
    1．重複傳送大型提示詞，增加 Token 成本：每次內部模型呼叫都附上完整靜態指令。 提示詞組裝層重複傳送大型 system／developer instructions，未依子任務縮減必要上下文。 精簡子模型提示詞，只保留必要指令與動態資料；對必須重複的靜態內容，使用平台支援的 prompt caching 或上下文重用，不能假設只傳 context ID 就能取得內容。以相同任務確認結果與必要工具流程不變，並比較 Token 用量與實際費用。
    2．重複呼叫工具，且擅自修改參數：重複搜尋或政策檢查，填入 EMP-UNKNOWN，重試時改動篩選條件。 工具編排層缺少單次請求內的結果重用、參數驗證，以及重試與平行派送時的參數一致性控制。 對同一請求內、相同工具與參數的唯讀查詢重用結果；未知的選填員工 ID 應省略，必填資訊則要求補充，不要捏造。保留原始搜尋條件，僅在明確要求重新搜尋時變更；確認不再出現無意義的重複呼叫或參數漂移。
    3．政策檢查完成，訂位仍被擋下：已呼叫 check_travel_policy，但 submit_booking 拒絕訂位。 compliance_summary 缺漏或格式不符，未帶入各旅程項目的政策證據；文件與實際驗證規則也可能不一致。 先核對兩個工具的 schema 與必填規則，再將政策結果映射為訂位所需的結構，送出前進行驗證。格式錯誤須明確回報，不可編造證據或放寬檢查；確認合規且證據完整的訂位可成功，真正不合規的訂位仍被阻擋。
    4．模型呼叫被取消，必要飯店搜尋未執行：尚未呼叫 search_hotels 就中止。 模型執行期間發生 CancelledError，編排層未完成必要搜尋，也未提供適當的恢復或失敗回報。 區分使用者主動取消、逾時與服務異常；僅對可恢復的暫時性失敗採有限次重試與退避。回覆前檢查必要搜尋是否成功，未完成時明確告知，不能憑空提供飯店結果；確認暫時性故障可恢復，使用者取消則確實停止。
    5．最終答案漏掉固定合規句，或錯誤插入：工具結果正常，但回覆未正確呈現允許證據。 回覆模板未依政策結果控制固定文句，導致改寫、漏寫，或在沒有對應允許證據時仍插入。 核對固定文句契約；當對應項目的政策結果為 hard_gate_blocked=false 且 cited_rule_ids=[] 時，在政策決策與證據區段原樣輸出 Allowed; policy tool returned no blocking CT rule.，不能改寫或無條件套用。確認符合條件時逐字出現，沒有對應允許證據時不得出現。
