    Act 3：讓它更好¶

    Make it better · 用同一份評分表（scorecard），衡量一次只改一件事的實驗。

    業務問題：更快或更省，是否讓團隊多花時間重新查核？ 對照設備維護資訊助理，漏掉重要限制的回答，不會因模型便宜就更值得採用。本幕用相同條件比較品質、回應效率與用量，讓取捨有依據。

    目標¶

    審閱 Rubric Evaluator 根據探索證據產生、且由講師凍結版本的評分表；用相同課堂題組比較 v1 與 Model Router v2。本場不執行模型微調或 Quality Router。

    項目 本幕安排
    現場主線 學員操作 · 必做：審查評分表，核對 v1／v2 比較，提出保留或不採用的理由。
    閱讀與觀察位置 教材、獲授權的 Microsoft Foundry Evaluations 與講師交付的比較輸出。
    原指令執行位置 主要 Ubuntu VM 的第二場專用 Terminal、第二場專案根目錄，指定本組環境。
    時間 依講師排程；雲端完成時間不作保證，逾時使用已驗證的本組預跑結果。

    前置條件¶

    比較契約要固定

    保持相同的 Testing 題目、重複次數、評分表版本與評分模型（judge）。本場 v2 相對 v1 只改模型選擇。課堂使用 classroom 六題一次；不能直接對比 full 的 24 題三次。詳見題量與公平比較。

    已備妥 Act 2 的可驗證證據、凍結評分表與本次實際版本，並符合課堂操作放行條件。版本不符的 Router 結果須隔離；未證明回應實際使用正確版本前，不將 v2 列為可比較結果。

    需授權／可能計費

    評分表草擬、評分與模型部署都可能產生費用。先確認 Act 2 的追蹤記錄與 Insights 已備妥，再由有權限的操作者從本場專案根目錄執行。

    操作步驟¶

    學員操作 · 必做¶

    1. 審閱評分依據。 在本組 Foundry 的 Evaluations → Evaluators 開啟講師交付的 evaluator ID 與版本，不只憑名稱判斷。評分檢視者將政策、查證、金額與誠實揭露面向各對應到業務指引或有效的 Insights／追蹤證據；缺少依據時先記錄，不自行改評分表。
    2. 取得同一條件的結果。 本組放行後，當輪操作者依 Step 6–7 取得六題一次的 v1／v2 評估；其餘組員核對題組、評分表、評分模型與回應實際版本。工作未完成或版本不符時停下來，不重送以補出比較表。
    3. 寫下採用理由。 紀錄者使用 Step 9 的比較紀錄，留下品質、最弱面向、延遲、Token 用量與來源。每人提出一個支持或反對採用 v2 的證據；本幕不切換共用端點。

    以下命令僅供已放行本組的當輪操作者執行

    未放行時只閱讀可驗證的本組匯出結果，不執行新的評分或部署，也不使用已隔離的結果。六題流程的本機測試不解除來源、Client 與線上驗證門檻。

    Step 5．審閱已凍結的評分表¶

    講師課前根據以下來源草擬本組 Rubric Evaluator，再人工審核並凍結版本；學員不各自重新生成：

    • v1 的實際 Exploring 追蹤記錄與 Agent 資訊。
    • Exploring 題目及理想回答的樣貌。
    • data/scorecard-guidance.json 的業務指引。
    • Act 2 儲存的 Insights 分析發現。

    Testing 的答案與預期結果不用於草擬評分表。可註冊 Testing 題集供後續評分，但不能因比較結果不理想就修改評分表，再沿用舊分數。

    審查草稿，不要只接受名稱¶

    讀取講師交付的本組評分表唯讀副本，記下 evaluator ID、版本、通過門檻與 gpt-5-mini 評分模型，確認每個面向都對應 Caldova 真正在意的事：

    • 差旅政策判定正確。
    • 推薦前先查證。
    • 金額與幣別加總正確。
    • 誠實說明沒有找到、沒有完成或沒有足夠證據的部分。

    Hosted Agent 的行為指示警告

    Foundry 可能顯示：

    Generated with input-quality warnings: The agent has no instructions.

    原指南說明，Hosted Agent 的行為指示封裝在程式碼與設定中，Rubric Evaluator 無法直接讀取。腳本會改以提示來源（prompt source）傳入行為指示與政策。請檢查草稿內容是否符合需求，不要只為消除這項已知警告而重建；其他真正的失敗仍要排查。

    Step 6．評分 v1¶

    操作性質：付費模型擷取與線上評分。 先確認本輪沒有其他重工作，再提交一次：

    bash infra/07-score.sh run --label v1 --cohort classroom \
  --environment "${AZURE_ENV_NAME:?請先完成本組環境交付}"

    本場課堂使用 6 道 Testing 題目、1 次評分，搭配本組固定的評分表版本與 gpt-5-mini 評分模型。這會產生模型與評分費用；擷取後的回答仍由線上服務評分，不是離線免費執行。

    Testing 使用其他題組沒有出現過的情境。先記下 v1 的分數，這才是往後比較的起點。

    bash infra/07-score.sh compare --cohort classroom \
  --environment "${AZURE_ENV_NAME:?請先完成本組環境交付}"

    確認有 v1 的實際結果、各難度與各評分面向，而不是只有成功提交工作的訊息。

    Step 7．建立 Model Router v2，並評分¶

    操作性質：建立／沿用版本與付費評分。 先核對 v2 是否已交付及目前使用中版本，再由核准操作者接續；不把版本建立成功當成回應綁定已驗證。

    bash infra/08-model-router.sh --mode balanced \
  --environment "${AZURE_ENV_NAME:?請先完成本組環境交付}"
bash infra/07-score.sh run --label v2 --cohort classroom \
  --environment "${AZURE_ENV_NAME:?請先完成本組環境交付}"

    行為指示相同，工具相同，唯一改變是模型的選擇：Balanced Router 只允許 GPT-5、GPT-5-mini、GPT-5-nano。先保留原本上線的版本，不帶 --activate。

    建立版本後還要核對真實回應的版本與執行階段證據；--version 參數、標籤或 CLI 成功都不足以證明實際綁定正確。缺少執行階段權限時，保留已記錄版本，請講師完成受控授權後再接續，不重複部署或自行授予資源群組權限。

    Step 7b 的 Quality Router 與 Step 8 的 fine-tuning 是原版延伸閱讀，不在本場共用環境執行，也不要求產生 v2-quality、v2-alt 或 student 版本。

    Step 9．比較，然後決定¶

    以下讀取同一課堂評估題組的結果，不提交新的評分工作；入口仍會檢查本場交付條件：

    bash infra/07-score.sh compare --cohort classroom \
  --environment "${AZURE_ENV_NAME:?請先完成本組環境交付}"

    預期畫面與證據¶

    原指南的比較包含兩張表：

    • 整體表：平均分數、相對 v1 的變化、通過率、難度、最弱面向、延遲與 Token 用量。
    • 面向表：各版本在評分表每個面向上的分數。

    讀懂一列比較結果¶

    先問「這些資料能比較嗎？」，再問「這個改版是否值得採用？」。以下對照實際比較表欄位，不提供假分數，也不將原版影片數字當成本組結果。

    欄位 看什麼 對業務決策的意義
    Version／Agent 比較表前者是 v1／v2 等標籤，後者是紀錄的 Agent 版本號；仍須回查實際回應。 v1 不一定等於實際版本 1；一列表格不是版本綁定正確的獨立證明。
    Rows scored 已取得有效分數的回答數；核對預期題數、實際回答、有效評分與錯誤紀錄。 本場完整的 classroom 是六題一次；缺漏先查來源，不因只留下成功樣本而宣稱改善。
    Mean score 平均品質與相對基準的變化。 平均較高不代表重要條件都守住，還要看分布與政策面向。
    Pass rate 依本組固定評分依據判定通過的比例。 與平均分數分開解讀；高平均也可能仍有不可接受的回答。
    Weakest area 本次最弱面向及各面向分數。 是否涉及事先約定的必要品質？不能讓少數高分掩蓋關鍵退步。
    P50 s／P95 s 中間位置與較慢端的 Agent 回答延遲，不是評分工作的等待時間。 看回應效率的取捨；六題樣本的 P95 不是正式服務 SLA 或吞吐驗證。
    Avg agent tokens Agent 回答的平均模型用量，不是評分模型或其他服務的總用量。 用量不是美元帳單；必須結合實際模型、價格與其他服務費用。

    任何題組、重複次數、評分表、評分模型或實際版本不一致，都先停在資料核對。程式的完整性檢查不是省略查證的理由；入口阻擋時也不繞過檢查拼湊一張表。

    依序確認：

    1. 差旅政策是否仍然正確？最弱的面向有沒有退步？
    2. 提升是否在各輪與未見過的 Testing 題目上維持？
    3. 只有品質維持時，再討論速度與成本。Token 數是用量，不是完整帳單。
    4. 相較自己的起點，這一步是往上、往下，還是證據不足？

    保留 v1 完全合理。 Model Router 沒有勝出，是有用的結果，不是要藏起來的失敗。六題一次是課堂練習，樣本有限，不因此推論正式服務已全面改善。

    小組判讀：評分模型也可能判錯

    使用已交付且獲准檢視的一筆回答、工具證據與判分理由，不另外提交工作：

    1. 評分檢視者指出判分依據，證據檢視者對照實際工具結果與必要條件。
    2. 記下「同意／有疑義／需要補資料」及理由；缺少判分理由就標記缺資料，不自行推測。
    3. 有爭議不直接改分、換評分模型或排除不喜歡的答案。若確認規準需改，由負責人凍結新版本，再按既有放行流程讓各比較版本使用相同條件重評。

    多輪取樣不會把錯誤規準變正確；通過門檻也不等於所有政策都零違規。可以核對 Testing 的評分理由，但不要把答案回填行為指示或練習題來反覆刷分。

    費用從哪裡來？¶

    Andre 關心的不是某一格用量變小，而是在品質條件下，整體取捨是否說得清楚。Router 即使用更多 Token，也可能因模型組合較便宜而降低推論費；反過來也可能成立，不能只看總 Token 數下結論。

    展開：模型用量之外的費用組成
    費用來源 為了做什麼 比較表是否涵蓋？
    Agent 推論 旅遊回答與工具使用過程中的模型呼叫。 提供 Agent 用量線索，但仍要核對實際模型及輸入／輸出價格。
    評分、Insights 與 Agent Optimizer 分析問題、產生／審閱規準、產生候選與評分。 不包含在 Avg agent tokens 的完整成本中，須另記錄。
    BYOK 開發助手 本組工程輔助、資料解讀與差異審查。 與業務 Agent 的用量分開看。
    執行環境與映像 Hosted Agent、Portal 運算，以及 ACR 建置與儲存。 依資源與服務型態計費，不能因未送旅遊請求就推定全部為零。
    觀測與資料 Application Insights／Log Analytics 的資料擷取、保留與儲存。 不在 Agent 平均 Token 數內。

    這是費用範圍說明，不是本場估價單。沒有完整帳單、模型組合與使用條件，就不推算每人費用、節省百分比或 ROI；容量配額也不是實際用量。

    本組比較紀錄¶

    下面是空白紀錄範本，不是已完成的實驗結果。請填在講師指定的受控位置；本站不儲存填寫內容，未執行與不可比較要分開記錄。

    共同比較條件 本輪填寫
    本組與執行來源 組別、環境、主要工作副本、執行 UTC 時間；註明現場或本組預跑。
    題集 classroom、固定六題、一次；記錄題目 IDs／題集雜湊。
    評分依據 evaluator ID、評分表版本、通過門檻、gpt-5-mini 評分模型與擷取模式。
    來源證據 擷取檔／評分結果位置、工作與 Response IDs；保留原始檔，不公開敏感追蹤記錄。
    標籤 實際版本、模型與行為指示雜湊 品質與用量 決策及理由
    v1 待本組填寫，不能只填標籤。 待填平均分數、通過率、最弱面向、延遲與 Token 用量。 待填；缺證據則標記尚未完成。
    v2 待核對實際回應版本；隔離資料不列入。 待填同一評估題組的結果。 待填採用／保留／不可比較與理由。
    v3（Act 4） 待填有效候選來源、起始版本與新版本。 待填相同六題一次的結果。 待填人工審查與重測後的決策。
    情境插畫：由人檢查變更

    插畫不是實際差異畫面或已完成評估；本組紀錄須連回真實來源。

    詢問 Copilot：把比較說成 hill climbing 
    以下是 bash infra/07-score.sh compare 的實際輸出：[貼上去識別化內容]。
請先確認評估題組、題數、重複次數、評分表、評分模型與回應實際版本相符，
再比較 v2 相對 v1 的品質、政策、延遲與用量。
哪一步值得保留？哪些變化可能是雜訊？不要預設較小的模型一定更划算。

    本幕先形成比較與建議，不切換共用端點。版本綁定不符、評分未完成或資料不一致時，記錄「不可比較」並停止；是否上線在 Act 4 依證據與授權決定。

    完成條件¶

    以下為自行核對清單，本站不儲存完成進度。

    • 能將評分表的業務面向追溯至指引與 Insights。
    • 已核對本次 Testing 題組、評分模型與評分表一致。
    • 能指出 v2 相對 v1 的唯一變更，以及政策與最弱面向是否維持。
    • 已記下採用、保留或證據不足的理由；沒有將被隔離的 Router 結果列入比較。
    • 未把 Token 用量當成完整費用，也未把未執行的選做實驗當成自己的分數。

    疑難排解¶

    狀況 下一步
    評分表有已知行為指示警告 檢查實際面向與原指南的提示來源，不只為隱藏警告而重建。
    缺少標籤或分數 確認該版本是否已建立、評分是否完成；不要自行猜版本編號。
    題量、評分表、評分模型或回應版本不一致 不混算分數；保存原始證據，由講師確認後再重新驗證。

    詳細處理方式見疑難排解。

    下一步¶

    這一步在 hill climbing 的位置¶

    我們建立高度計、衡量起點、走了一個可比較的單步，並只保留有證據的進步。下一幕讓 Agent Optimizer 多嘗試幾步，但人仍然負責決定。

    這一步的業務意義，是支援「是否值得採用」的討論；不是把速度、Token 用量或平均分數的排名直接當成營運價值。
