    Act 4：擴大改善規模¶

    Make it scale · Agent Optimizer 負責嘗試，人負責審查與決定。

    業務問題：需求或模型改變時，如何加快改善，又不失去人的掌控？ 對照設備維護資訊助理，變更要能說明理由，結果要能重新核對。本幕擴大的是改善流程，不是宣稱已完成流量擴展、壓力測試或高可用驗證。

    目標¶

    讓 Agent Optimizer 提出 Agent 行為指示（instructions）的調整，用練習題（practice）挑選候選方案（candidate），再用相同 Testing 題組重新驗證。自動化不應跳過人工審查，也不應讓未驗證的版本意外上線。

    項目 本幕安排
    現場主線 學員操作 · 必做：審查候選方案的行為指示，以練習題／Testing 證據提出人工決策。
    閱讀與觀察位置 教材、獲授權的 Microsoft Foundry Optimize，以及講師提供的差異畫面與評分。
    原指令執行位置 主要 Ubuntu VM 的第二場專用 Terminal、第二場專案根目錄，指定本組環境。
    時間 待講師試跑確認；雲端工作的等待與現場閱讀、討論分開。

    前置條件¶

    練習題分數不是最終證明

    Agent Optimizer 使用 Exploring 中的 12 道練習題。本場課堂以 6 道 Testing 題目、1 次評估與固定評分表，比較候選方案和起點；課前完整評估的 24 題三次另列，不能混比。

    需授權／可能計費

    本幕需要 Act 3 的評分表、基準版本（baseline）分數與選定的起始標籤。Agent Optimizer、部署與重新評分可能計費；取得授權後，從本場專案根目錄執行。

    未放行不提交；沒有有效候選就停在證據審查

    本組須依課堂操作放行條件取得明確授權。取消、失敗或狀態不明的工作，不因教材公開就能再次提交。沒有有效候選就記錄「尚未完成」，不拿原版畫面或被取消工作的候選冒充可發布結果。

    操作步驟¶

    學員操作 · 必做¶

    1. 核對本輪工作。 在本組 Foundry 的 contoso-travel → Optimize 或已交付的 status 輸出中，證據檢視者核對起始標籤／實際版本、工作 ID、12 道練習題、評分表與完成狀態。取消、失敗或狀態不明就記錄並停止，不因看到候選方案名稱就執行 apply。
    2. 開啟真實差異。 本輪已有有效候選方案並獲准下載後，當輪操作者在 VS Code Explorer 對起點保留的行為指示檔案選 Select for Compare，再對本輪候選檔案選 Compare with Selected。指示檢視者逐項說明變更對應哪項有效分析發現／追蹤記錄；只讀取差異，不覆寫基準或自行接受全部變更。
    3. 重測並作決定。 只有候選方案、部署與實際版本均通過檢核，才接續 Step 11。紀錄者將相同六題一次的結果填入 Act 3 比較紀錄，全組提出發布或保留理由，再交由獲授權者決定是否切換。沒有有效候選方案時就記錄阻礙，不製作假差異畫面或分數。
    本組已放行、且沒有在途工作時：Step 10，提交一次 Optimizer

    課程前：讓 Agent Optimizer 提出候選方案¶

    Step 10．提交行為指示實驗¶

    從 Act 3 的有效比較選定起點。以下只示範以 v1 為起點的命令，僅於本組明確核准後執行，不表示 v1 必然最好。 其他起點請使用講師核對後的命令，不套用被隔離的 v2：

    bash infra/10-optimize.sh submit --from-label v1 \
  --environment "${AZURE_ENV_NAME:?請先完成本組環境交付}"

    Agent Optimizer 會提出三種行為指示候選方案，以練習題試跑，使用同一份 Rubric Evaluator 評分表評分。腳本會記住工作，後續可以查看：

    bash infra/10-optimize.sh status --from-label v1 \
  --environment "${AZURE_ENV_NAME:?請先完成本組環境交付}"

    需要持續等待時：

    bash infra/10-optimize.sh status --watch --from-label v1 \
  --environment "${AZURE_ENV_NAME:?請先完成本組環境交付}"

    工作在 Foundry 執行，關閉終端機不會取消工作。已有 operation ID 或狀態不明時只查狀態，不再次 submit；被取消的工作也不自行重送。可在本組 contoso-travel → Optimize 核對。

    本場使用目前已適配的 Agent Optimizer 介面：gpt-5 產生行為指示候選方案，gpt-5-mini 評分；不是原版舊介面使用的 eval.yaml。Client 工具已安裝不等於此流程已通過線上驗證。

    驗證候選方案已備妥¶

    • 核對工作是否完成、起始標籤是否正確。
    • 比較每個候選方案與基準版本的練習題分數。
    • 查看 Token 用量、時間與各面向，不只看最佳候選方案的星號。
    • 明確區分「已提交」「已完成」「已建立版本」與「已上線」。
    詢問 Copilot：先解讀練習題結果 
    以下是 bash infra/10-optimize.sh status 的輸出：[貼上去識別化內容]。
請將候選方案與基準版本比較，說明練習題分數、Token 用量與時間。

不要替我下載、部署或切換使用中版本。

    課程中：人工審查候選¶

    不直接採用「Deploy best candidate」¶

    Foundry 的星號與建議來自練習題分數。原指南刻意不直接使用 Deploy best candidate，也不在 apply 後直接執行一般的 azd deploy：

    1. 練習題提升還沒有經 Testing 驗證。
    2. 候選方案應先成為可評分的新版本，不應直接改變操作網站。
    3. 原專案的每個版本使用自己的設定；一般 azd deploy 可能仍指向基準版本，並重建不需要的操作網站。

    我們仍然透過腳本呼叫 optimize apply 下載檔案，但以受控的發布腳本建立版本。

    下載並比對行為指示¶

    本輪已有有效候選方案、且核准下載時：選取候選方案

    延續已核准的 v1 起點示範。當輪操作者從本輪有效工作選取經核准的候選方案 ID；不使用取消或其他組工作的 ID：

    read -r -p "輸入本輪核准的 candidate ID：" CANDIDATE_ID
bash infra/10-optimize.sh apply --from-label v1 \
  --candidate "${CANDIDATE_ID:?尚未選定有效候選}" \
  --environment "${AZURE_ENV_NAME:?請先完成本組環境交付}"

    並排閱讀：

    • src/agent/.agent_configs/<candidate-id>/instructions.md
    • src/agent/.agent_configs/baseline/instructions.md

    上面的 baseline 路徑對應本頁的 v1 起點示範。若核准的起點不同，改與該實際版本保留的行為指示比較，不一律拿原始 v1 當基準。apply 下載候選方案供審查，不代表部署或上線；模型與工具必須維持起點設定。

    逐項確認：

    • 改變了哪些行為？是否仍符合 Caldova 的差旅政策？
    • 回應了哪一項 Insights 分析發現？
    • 是否要求 Agent 根據工具回傳結果說明限制，而不是捏造完成？
    • 是否有直接複製練習題的答案，造成只會背題的風險？
    原版審查畫面參考，不是本輪候選差異

    來源：Microsoft 原始投影片第 42 頁，裁切保留候選審查重點，採 CC BY-SA 4.0。圖中的分析發現與追蹤記錄數來自原版示範，不是本組結果。本輪差異畫面必須來自實際核准的起點與候選檔案，不能由這張圖推定已完成 apply 或部署。原始來源。

    請比較候選方案與基準版本的 instructions.md。
每項變更對應 .azure/<env>/insights/findings.json 的哪些發現？
哪些問題仍未解決？有沒有直接複製練習題目或改變政策要求？
請附上證據，未經我核准不要修改檔案或部署。

    Step 11．建立 v3，再做 Testing¶

    已核准候選與部署時：建立 v3，再做相同課堂評估

    候選方案經審查與授權後，建立有標籤的版本：

    bash infra/11-promote.sh deploy \
  --candidate "${CANDIDATE_ID:?請先選定並審查有效候選}" \
  --environment "${AZURE_ENV_NAME:?請先完成本組環境交付}"
bash infra/07-score.sh run --label v3 --cohort classroom \
  --environment "${AZURE_ENV_NAME:?請先完成本組環境交付}"
bash infra/07-score.sh compare --cohort classroom \
  --environment "${AZURE_ENV_NAME:?請先完成本組環境交付}"

    這次只改行為指示，模型應與起點一致。保留原本上線的版本，再核對 v3 回應的實際版本；若缺少執行階段權限或綁定不符，停止並由講師處理，不能僅憑標籤或成功退出就計入比較。

    Promoted 不等於已上線

    Foundry 的 Agent Optimizer 工作可能顯示 Promoted: v<N>，表示候選方案已建立為版本。是否提供預設流量，仍由端點的使用中版本決定。

    預期畫面與證據¶

    用同一個高度計做決定¶

    比較 v3 與自己的起始版本：

    1. Testing 的品質提升是否維持，而不只是練習題更好？
    2. 政策相關面向是否仍然正確？
    3. 最弱面向、延遲與 Token 用量的代價是什麼？
    4. 證據是否足以發布，或應維持原狀？

    交接紀錄至少包括候選方案 ID、起點／新版本、行為指示雜湊、練習題與 Testing 的來源、部署及重測狀態。用 Act 3 的同一份比較紀錄說明取捨，不把候選排序當成發布核准。

    情境插畫：比較證據後，由人決定

    插畫不是本次分數或發布紀錄；是否上線以本組有效證據與核准為準。

    需授權／可能計費 · 選做：確認 Testing 後才切換使用中版本

    切換會影響端點的預設流量；後續模型呼叫可能計費，不是每位學員的必做動作。若 v3 符合需求，經授權後才上線：

    bash infra/11-promote.sh go-live --label v3 \
  --environment "${AZURE_ENV_NAME:?請先完成本組環境交付}"

    在操作網站開啟新對話，核對目前使用中版本。若 Testing 沒有維持改善，保留原版本；這表示驗證機制有發揮作用。

    詢問 Copilot：應該讓 v3 上線嗎？ 
    請比較 Agent Optimizer 的練習題結果與這份 compare 的 Testing 結果：
[貼上去識別化內容]。
v3 相對自己的起始版本改善了什麼？政策與最弱面向有維持嗎？
請列出支持發布與維持原狀的證據，不要替我執行 go-live。

    v3-router、工具修正與學生模型訓練是原版的後續延伸，不是本場可自行加跑的步驟。若懷疑問題在工具或資料，記錄證據交給講師，不同時改多項設定來追求分數。

    完成條件¶

    以下為自行核對清單，本站不儲存完成進度。

    • 能指出 Agent Optimizer 起點、候選方案與其處理的 Insights 問題。
    • 已區分 12 道練習題、課堂六題一次與完整 24 題三次，不混用其分數。
    • 能說明建立版本、Foundry 顯示 promoted 與端點上線的差別。
    • 有保留或發布的實際證據與理由；未執行的部署、選做或切換不算已完成。
    • 理解授權者決定是否上線，並維持題組隔離與單步實驗契約。

    疑難排解¶

    狀況 下一步
    工作只有提交、尚未完成 記錄目前狀態，不重複提交，也不宣稱已取得候選分數。
    練習題提升但 Testing 未維持 保留已驗證的版本，不以示範分數取代本次結果。
    部署中斷或操作網站版本不符 由獲授權者確認原先使用中的版本標籤，再依疑難排解處理。

    下一步¶

    完成本輪紀錄：起始版本、有效候選方案、相同題組的重測結果，以及發布／保留／尚未完成的決策。尚有在途工作或阻礙時一併交接，不為收尾而重送或切換版本。

    這一步的業務意義，是讓改版有理由、審查有依據、決策可追溯；有效比較後保留原版，與證據不足而尚不能決策，也要分清楚。

    下一步：回顧與結論。 在結論集中回顧四幕方法、三位角色的需求，並完成兩分鐘摘要。
