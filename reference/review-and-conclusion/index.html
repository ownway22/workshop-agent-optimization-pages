    回顧與結論¶

    這堂課要帶走的不是「哪個模型最好」，而是當模型、價格與業務需求改變時，仍能重複使用的 Agent 改善方法。

    觀察 → 理解 → 衡量 → 只改一件事 → 重新測試 → 決定 → 重複。

    回顧方法，不預設實驗結果

    以下是依原始教材整理的學習重點，不是本次雲端執行的成果報告。請以自己獲授權執行或講師交付的追蹤記錄、評分表與比較結果說明；只閱讀教材，也可以用它們核對自己的理解。

    回顧四幕：從能運作到持續改善¶

    階段 核心問題 應該帶走的證據或能力
    Act 1：先讓它運作 有一個可以觀察的起點嗎？ 確認講師課前交付的本組 v1、本人登入與基準證據；不由學員重建環境。
    Act 2：找出表現不佳的地方 哪些問題反覆發生？ 從重複提問的追蹤記錄與 Insights 分析發現找出規律，區分行為指示、工具與資料的問題。
    Act 3：讓它更好 這一步真的有幫助嗎？ 審閱凍結的 Rubric Evaluator 評分表，以相同六題一次比較 v1 與 Balanced Router v2；不執行模型微調。
    Act 4：擴大改善規模 如何多做嘗試，又不失去掌控？ 審查 Agent Optimizer 提出的行為指示，先看練習題，再用保留的 Testing 題組驗證，由人決定是否發布。

    四項 Foundry 功能不是各自獨立的展示：Insights 找出問題，Rubric Evaluator 定義衡量方式，Model Router 提供一個可測試的變更，Agent Optimizer 則加快候選方案的探索。 GitHub Copilot 協助閱讀證據、比較差異與串接可重複執行的工作流程，不代替人的核准。

    判斷改善的五個原則¶

    1. 先知道起點。 保留基準版本的標籤、評分表與實際分數，不憑模型名稱推論品質。
    2. 一次只改一件事。 比較模型、行為指示或工具／資料時，都要明確指出相對哪個版本做了什麼變更。
    3. 用同一個高度計。 固定題集、重複次數、評分表版本與評分模型，並核對回應實際版本。課堂六題一次不能與完整 24 題三次混比，Agent Optimizer 的練習題分數也不是最終證明。
    4. 先守住政策與品質，再談速度與成本。 除了平均分數，也看最弱面向、不同難度與多輪差異；Token 用量不是完整帳單。
    5. 人決定是否採用。 建立版本、Foundry 顯示 promoted、切換使用中版本是不同的事。經過審查、Testing 與授權後，才決定是否讓預設流量使用候選方案。

    不同結果，都能帶來下一步¶

    下表是假設情況與判讀方式，不表示這次實驗一定會得到相同結果。

    如果這次的證據顯示…… 可以得到什麼結論？
    v2 在維持政策與品質下改善速度或成本 Model Router 對這個工作負載是值得保留的方向，不代表它適合所有需求。
    v2 沒有勝過 v1 保留 v1 是合理決策；一次單步實驗讓我們更清楚哪些方向不該直接採用。
    v3 的練習題分數提升，也在 Testing 維持改善 Agent Optimizer 找到值得審查的候選方案，但是否上線仍須檢查政策、代價與授權。
    v3 的練習題分數提升，Testing 卻沒有維持 維持原版；這正是將練習題與最終評分分開的價值。
    回應版本不符，或題集、評分表／評分模型不一致 結果不可比較。保留原始證據並交由講師處理，不用變更標籤或排除失敗資料來製造改善。
    工作受阻，且沒有可驗證的本組預跑結果 明確記錄尚未完成，不拿原版影片或其他組分數替代，也不據此發布。

    保留原版、退回上一版，或拒絕候選，都可以是正確結果。真正要避免的是跳過衡量。

    回到 Caldova：三種需求，同一套證據¶

    原指南用三位角色提醒我們，最佳化不只是技術分數：

    • Krystal：政策判定可靠。 不能因為更快或更便宜，就讓不符合差旅政策的版本上線。
    • Andre：比較有依據。 能用一致的品質、延遲與用量資料解釋取捨，而不是只說某個模型比較強。
    • Lydia：流程可以重複使用。 下個月有新模型或需求改變時，可以沿用同一套觀察、衡量與決策方法，而不是重新猜一次。

    套用到半導體團隊：期待效果與量測¶

    我們希望減少猜測，讓資訊查核、交接與改版取捨更有依據。下表是可驗證的價值假設，不是本場已量得的客戶成效：

    業務期待 本場可以核對的證據 導入後另行量測的效果
    減少資訊查找與反覆查核 資料來源、工具回傳結果及限制是否說清楚。 查證時間、人工重查次數。
    改善交接品質 是否區分已完成、未完成與待確認內容。 交班漏項、補件或往返確認次數。
    在品質條件下控制等待與費用 同一題組的品質、延遲與模型用量。 使用者端到端完成時間、完整服務費用。
    讓變更更可掌握 基準／候選版本、重測與人工決策紀錄。 變更審查時間、回退演練結果。

    旅遊與設備維護工作的資料、規則與風險不同；可轉移的是驗證方法，不是原分數或規則。本場六題課堂評估不能直接換算成良率、稼動率、停機時間或 ROI 的改善；正式場域仍需授權資料、適當評估與既有安全流程。

    用兩分鐘說明你的決策¶

    依本次可取得的證據，回答五個問題：

    1. 起始版本是什麼？最需要改善的業務或政策問題是什麼？
    2. 每次實驗相對起點只改了哪一件事？
    3. 哪些追蹤記錄、Insights 分析發現與 Testing 結果支持你的判讀？
    4. 品質、最弱面向、速度與成本之間有哪些取捨？
    5. 你建議保留、採用，還是繼續收集證據？下一個值得驗證的單步是什麼？

    把方法帶回自己的 Agent¶

    從一個具體需求開始：選定要改善的問題，留下基準版本，以可追查的執行追蹤記錄建立評分依據，再提出一項變更、重新測試與審查。這就是把 Foundry 可觀測性、GitHub Copilot 工作流程與 hill climbing 組成可重複使用的 AgentOps 方法。

    最終交付：一份能說明決策的證據包¶

    索引本組既有紀錄即可，不是再跑一套流程。完整性比漂亮的平均分數更重要；以下檢核不代表目前每組都已有這些成果：

    • 基準：交代組別、環境、標籤／實際版本、模型、行為指示雜湊與執行時間。
    • 觀測：保留可追溯的回答／追蹤識別資訊、分析時間窗及有效分析發現；沒有發現、分析失敗與未取得資料分開記錄。
    • 評估：標明題目 IDs／題集雜湊、六題一次或完整預跑、評分表版本、評分模型與來源，連同有效評分數和錯誤說明。
    • 變更：有有效候選才附起點、候選 ID、真實差異與新版本；沒有候選就留下阻礙，不製作假差異或補造分數。
    • 決策與交接：說明採用／保留／需補證據的理由、實際使用中版本或尚未切換，以及在途工作與結果位置。

    使用 Act 3 比較紀錄串起這份索引；私有原始證據與去秘密匯出副本分開保管，不將整個 .azure/ 當作交付包或公開附件。

    帶回公司的小型驗證卡¶

    先用兩分鐘摘要回顧本場實驗，再用這四格提出一個回公司後可驗證的假設。不要求現在啟動新服務，也不把 Travel 的成績直接移用到設備維護工作。請在自己的受控筆記填寫，網站不儲存內容。

    要想清楚的事 你的驗證構想
    想先改善哪一項資訊工作？ ＿＿＿；例如設備維護資訊查找與交接，只選一個範圍。
    不能犧牲的品質或限制是什麼？ ＿＿＿；例如資料依據可追溯、限制說清楚，並由既有授權流程確認。
    第一個要量測的效果是什麼？ ＿＿＿；寫下量測方法，例如查證時間或人工重查次數，不先填節省百分比。
    下一次只改哪一件事？ ＿＿＿；先確認資料範圍與核准，再選一個變因，不同時改模型、行為指示與工具。

    值得帶走的不是「一定改得更好」的保證，而是能說明採用、保留或需要更多證據的理由。設備維護資訊助理在這裡只是產業對照，並非本場已實作的設備判斷、派工或控制功能。

    有操作問題時，前往疑難排解；要繼續學習，可從資源與授權找到原始教材、投影片與官方技術文件。
