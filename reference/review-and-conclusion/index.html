    持續改善 Agent 的循環¶

    這堂課要帶走的不是「哪個模型最好」，而是當模型、價格與業務需求改變時，仍能重複使用的 Agent 改善方法。

    觀察 → 理解 → 衡量 → 只改一件事 → 重新測試 → 決定 → 重複。

    • 先知道起點，保留基準版本的標籤、評分表與實際分數，不憑模型名稱推論品質。
    • 一次只改一件事，比較模型、行為指示或工具／資料時，都要明確指出相對哪個版本做了什麼變更。
    • 用同一個高度計，固定題集、重複次數、評分表版本與評分模型，並核對回應實際版本。課堂六題一次不能與完整 24 題三次混比，Agent Optimizer 的練習題分數也不是最終證明。
    • 先守住政策與品質，再談速度與成本，除了平均分數，也看最弱面向、不同難度與多輪差異；Token 用量不是完整帳單。
    • 人決定是否採用，建立版本、Foundry 顯示 promoted、切換使用中版本是不同的事。經過審查、Testing 與授權後，才決定是否讓預設流量使用候選方案。

    四項 Foundry 功能不是各自獨立的展示：Insights 找出問題，Rubric Evaluator 定義衡量方式，Model Router 提供一個可測試的變更，Agent Optimizer 則加快候選方案的探索。 GitHub Copilot 協助閱讀證據、比較差異與串接可重複執行的工作流程，不代替人的核准。
