    結論¶

    我們從操作差旅助理出發，查看 Agent 如何執行任務、問題留下什麼證據，以及如何評估改善方向。本場要帶走的不是「哪個模型最好」，而是讓 Agent 從「能運作」走向「有證據地變好」的方法。


    四個 Act，串成一套改善方法¶

    階段 本場操作 帶走的重點
    Act 1：先讓它運作 執行四個差旅情境，查看決策橫幅與工具回傳結果。 回答流暢，不代表政策判定與任務結果都正確。
    Act 2：找出表現不佳的地方 查看 Trace，以及 Insights 的分析發現與改善建議。 從「感覺有問題」，走向有證據、可行動的改善方向。
    Act 3：讓它更好 檢視 Rubric Evaluator 的維度、描述與權重，以及 Model Router 設定。 好不好要依業務標準衡量，模型選擇也需要權衡品質、速度與費用。
    Act 4：擴大改善規模 查看已完成的 Optimize Run，理解候選方案的 Score、Avg tokens 與 Avg latency。 自動化可以增加嘗試，但候選仍需要人來判讀與驗證。

    這些畫面不是各自獨立的展示——Trace 讓我們追查一次回答，Insights 歸納反覆問題，Rubric Evaluator 定義衡量方式，Model Router 提供模型選擇的改善方向，Agent Optimizer 則加快候選方案的探索。

    分數提高之後，還要看什麼？¶

    Optimize 畫面中，分數較高的候選方案，也可能需要更多 Token 或更長的回應時間。分數最高，不等於最值得採用。 請一起看三件事：

    • 品質：政策、證據與金額等重要面向，有沒有維持要求？平均分數不能掩蓋關鍵政策錯誤。
    • 效率：品質的改善，是否值得增加的等待與用量？Token 用量是費用線索，不是完整帳單。
    • 可信度：比較是否採用相同評估標準？正式採用前，還需要用未參與候選調整的代表性題目重新驗證，不能只看這次 Run 的排名。

    最佳化不是把單一分數推到最高，而是在不能犧牲的品質條件下，找到適合業務的取捨。

    回到業務：這些改善為誰而做？¶

    回到一開始的三位角色，他們需要的不只是更強的模型：

    • 旅客 Krystal：需要符合政策、結果說清楚，而且能繼續處理的差旅協助，不只是完整的回答文字。
    • 財務長 Andre：需要能說明品質、速度與費用取捨的數據，而不是「這個模型比較強」。
    • 架構師 Lydia：需要可持續使用的改善流程。下次模型或需求改變時，不必重新猜一次。

    對半導體團隊，也可以用相同方法思考設備維護知識助理：回答能否追溯依據、資訊不足時是否說清楚、不同方案的品質與等待時間如何取捨。可以轉移的是這套驗證方法，不是差旅案例的規則或分數；這也不是本場已驗證的設備維護成效。

    持續改善，先記住三件事¶

    1. 先看證據，再決定改什麼：從 Trace 與 Insights 找出問題，不只憑一次回答或模型名稱做判斷。
    2. 用相同標準比較，一次只改一件事：知道起點、看清差異，再重新測試，才知道變更是否有幫助。
    3. 讓自動化多做嘗試，由人決定是否採用：候選方案是待驗證的提案，不是上線承諾。

    這就是本場的 Hill climbing：

    觀察 → 理解 → 衡量 → 只改一件事 → 重新測試 → 決定 → 重複。

    沒有勝過原版，也是一個有價值的結果——我們更清楚哪個方向不適合。真正要避免的是沒有衡量就採用。

    把方法帶回自己的 Agent¶

    請用本場看到的畫面，想想三個問題：

    1. 我能指出一項有 Trace 或 Insights 支持的問題嗎？
    2. 我的 Agent 最不能犧牲的品質要求是什麼？
    3. 面對分數較高的候選方案，我還會確認什麼才建議採用？

    模型會變，需求也會變；真正值得帶走的，是用證據判斷、用一致標準比較，再由人決定的改善方法。
